# 本仓版本更新记录（re 线）

> 这里只记**本仓（re 线）自己做了什么**——Android 壳、壳侧叠加层、热更链、构建与同步流程。
> 游戏规则/数值的修订是上游的工作，记在 [CHANGELOG.md](../CHANGELOG.md)（上游原样保留）。
>
> **每出一版都必须在这里加一节**。`apk-re` 出包时会从本文提取对应版本段落写进 Release 说明；
> 找不到对应段落就退回按提交历史自动生成（见 §4）。

---

## 1. 版本号的读法

| 字段 | 含义 | 来源 |
|---|---|---|
| `shell-v<版本>-vc<versionCode>` | Release tag | `<版本>` = 上游 tag 去掉 `v`；`versionCode` 严格递增 |
| `versionName` | 上游官方版本号 | 跟随上游最新 tag（硬门禁，见 [BRANCHES.md](BRANCHES.md) §3） |
| `versionCode` | 构建序号 | 每次出包 +1，不回退 |

例：`shell-v0.3.3-vc2065` = 上游 v0.3.3 + 本仓第 2065 号构建。

**同一个 `versionName` 可以对应多个 `versionCode`**（上游没发新版，但本仓修了壳侧 bug）——这正是本仓存在的主要场景。

---

## 2. 怎么写一节

复制这个骨架，放在 `## 3. 记录` 的最上面（最新在上）：

```markdown
## shell-v0.3.3-vc2066 — 2026-11-04

**对应上游**：v0.3.3（未变）
**类型**：壳侧修复 / 新功能 / 仅热更

### 用户能感觉到的变化

- ……（一句话说清玩家会遇到什么不同；没有就写「无可见变化」）

### 修了什么

- ……（bug 的现象 + 根因一句话 + 影响范围）

### 需要注意

- ……（升级是否要重装、热更能否覆盖、存档/配置有没有迁移）
```

写作要求：

1. **先说玩家能感觉到什么**，再说技术细节。玩家读 Release 页面时只关心前者。
2. 提到 bug 要写**现象**（「进服后黑屏」）而不是只有代码术语（「TDZ 报错」）。
3. 涉及热更兼容性的必须写明：老 APK 能不能收到、要不要重装。
4. 不写「优化了体验」这类空话；写清楚优化了什么、快了多少。

## 3. 记录

## shell-v0.3.3-vc2067 — 2026-11-04

**对应上游**：v0.3.3（未变）
**类型**：壳侧修复

### 用户能感觉到的变化

- **房主开房后，房间会出现在大厅的房间列表里了**。之前房间发布指向一个已经改作他用的
  域名，请求全部打空，房间只有拿到房间码的人能进，别人在列表里看不到。
- 装这一版之后，进「大厅」能看到自己（和别人）公开的房间。

### 修了什么

三处配置全错，串起来就是「发布永远打空」：

- 房间目录地址指向了 o2p-platform（P2P 房间服务，**不接收房间**，返回一段说明文本）；
- 发布路径缺 /api（房间板端点是 POST /api/rooms）；
- 字段名不匹配（发 name，房间板要 serverId + serverName）。

### 需要注意

- **必须装新 APK**：这三处都在壳侧 Java（HostService / ShellConfig），热更覆盖不到。
- 但**老 APK 的房间发布也能修好**：房间板新增了 GET /dl/config.json，APK 会拉它覆盖
  内置默认值——那份配置原来托管在一个同样被接管的域名上，所以老设备一直拿不到新值。
- 公开房间仍然是**主动行为**（大厅面板里点「公开」才会发布），不会默认暴露。

### 技术要点

- serverId / serverName 取服务器身份（ServerConfig.serverId()），拿不到时退回
  shell-host / 房主服。**兜底值刻意避开房间板的保留值**（sp-phone-host / local /
  auto）——那些会被拒，且会造出「看得见但谁都进不去」的幽灵房。
- 实测确认：修好后的请求建房成功，GET /api/rooms 能列出该房间（含 serverId 与 mode）；
  保留值确实被 BAD_SERVER 拒绝。

## shell-v0.3.3-vc2066 — 2026-11-04

**对应上游**：v0.3.3（未变）
**类型**：壳侧新功能

### 用户能感觉到的变化

- **无可见变化**。这一版只加了一个后台统计用的匿名心跳，玩家侧完全感知不到。
- 顺带把崩溃上报的服务端补上了（上一版 vc2065 的 APK 已经有客户端代码，但服务端
  `/api/crash` 当时还没部署，上报会静默失败）。装这一版之后崩溃上报才真正端到端可用。

### 修了什么

- 服务端 `/api/crash` 已部署（之前 405/404）：APK 崩溃会自动加密上报，不再白跑。
- 后台 `/admin` 不再对所有人公开：无令牌只返回一个极简登录壳（不含任何后台结构、
  接口路径、实例信息），带令牌才给真页面。

### 需要注意

- **需要装新 APK**：心跳是壳侧 Java 代码，热更覆盖不到原生层。不装也能正常玩，
  只是后台看不到这台设备。
- **不申请任何权限**：安装 ID 是本机生成的随机串（16 字节），不含 IMEI/MAC/账号，
  不报机型/系统/IP。卸载重装会换新 ID。
- 静态资源已迁到魔搭数据集（CSS/字体/JS/JSON），Worker 只留 HTML 与 API——
  这是为了把 Deno 免费额度省给接口。

### 技术要点

- 心跳只在**冷启动发一次**，不做定期心跳：定期会把请求量放大两个数量级，
  而 Deno 免费额度只有 1M 请求/月。
- 服务端存储：`['apk-hb', id]`（48h 过期）+ `['apk-hb-daily', day]`（8d 过期），
  同设备 60 秒内防抖。统计口径 = 24 小时窗口内去重设备数。
- 管理后台新增「APK 在线」一栏：24h 设备数、今日新增、版本分布、近 7 天活跃。

## shell-v0.3.3-vc2065 — 2026-11-03

**对应上游**：v0.3.3（未变）
**类型**：壳侧新功能

### 用户能感觉到的变化

- **崩溃会自动上报了**。以前 APK 崩了只能靠截图描述；现在崩溃时自动把加密的诊断信息发出去，开发者能直接看到栈和设备信息。
- 游戏内「设置 → 问题反馈」显示的仓库地址改指本仓（原先指向上游作者的仓库），玩家照着地址提 issue 会提到这里。

### 修了什么

- 反馈转交链路缺一步反序列化：KV 里存的是 JSON 字符串，读的时候没 `JSON.parse`，于是转交给 GitHub 的 issue 正文里所有字段都是 `undefined`。**受影响的是 2026-10-13 至 11-03 之间的 31 条反馈 issue**（全部是同一份记录的重复转发，已关闭）。
- 分块存储的截图在转交后没有被清理（同样因为读到的是字符串，`chunks` 恒为 0），会长期占用 KV。

### 需要注意

- **不需要重装**：崩溃上报是壳侧 Java 代码，必须靠新 APK 才生效（热更覆盖不到原生层）。所以这一版**必须装新 APK**才能用上崩溃上报。
- 反馈地址的改写是热更层（`extras/feedback-url.js`），老 APK 收到热更后也会生效。
- 崩溃上报需要服务端配置 `CRASH_PRIV_KEY`（对应公钥已内置在 APK）；服务端没配的话上报会返回 400，静默失败，不影响游戏。

### 技术要点

- 公钥加密：RSA-2048 OAEP(SHA-256) 包裹一次性 AES-256 key，AES-GCM 加密正文。APK 里只有公钥，反编译拿不到私钥。
- **崩溃路径必须同步落盘**：`setDefaultUncaughtExceptionHandler` 返回后系统立刻 `killProcess`，后台线程来不及联网。所以崩溃时只做「加密 + 写文件」（毫秒级），下次启动再补发。
- 队列按三种结果分流：没网→保留重试、HTTP 4xx→删该条（毒丸）、429/5xx→保留。
- 服务端对崩溃正文做了脱敏（房间号、服务器地址、token、IP、长哈希），因为正文会进**公开** issue。

## 4. 自动生成（兜底）

`apk-re` 出包时按这个顺序取 Release 说明：

1. 本文里找 `## shell-v<版本>-vc<versionCode>` 这一节，**存在就用它**。
2. 不存在 → 从上一个 release tag 到当前 HEAD 的提交历史生成，按 conventional commit 前缀分组（`feat` → 新功能、`fix` → 修复、其余归「其他改动」）。
3. 两条都为空 → 只有一句「版本号 + 构建号」，并在日志里 `::warning::` 提示「本版没有写更新说明」。

**所以：正式发版请务必在本文加一节**，否则玩家在 Release 页面看到的只有自动生成的提交标题。

生成脚本：`tools/apk/release-notes.mjs`（用法见文件头）。
