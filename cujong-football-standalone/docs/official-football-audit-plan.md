## 1. 审计结论

### 当前基线（不是通过验收）

| 子系统 | 当前状态 | 审计结论 |
|---|---|---|
| 场景 | IMPLEMENTED | three.js 程序化几何可显示；不是官方场景资源本体。可选地面贴图只在本机提取后出现。 |
| 干员 | IMPLEMENTED | 仅固定的 6 个候选 ID；运行时自动生成 3v3，没有正式编队、待部署区、拖放部署与技能模型。 |
| 移动/动作 | IMPLEMENTED | 有摇杆/WASD 手动驱动和 AI 网格寻路；这把角色做成了动作游戏单位，不符合阵地足球的部署—自动作战循环。 |
| 足球 | IMPLEMENTED | 十类球参数有独立模块，但运动尺度、碰撞与实际部署/位移技能的联动仍是近似。 |
| 费用/再部署/技力 | BASELINE | 缺失完整生命周期；不能使用官方节奏作战。 |
| 技能/位移带球 | BASELINE | 缺少干员技能数据、SP、技能释放和按球重量判定位移带球。 |
| 对手 AI | IMPLEMENTED | 仅“追球/站位”简化 AI；无正式击球手、守门员、击人手角色和 4 种球队战术。 |
| 比赛风格 | IMPLEMENTED | 现有六种风格是人为简化增减益，不是官方完整效果；携带物未形成完整的部署触发机制。 |
| 阵地足球关卡阶段 | BASELINE | 只有单一 5 分钟比赛；没有初级/高级/特级参数与每次射门后全员撤退/再部署循环。 |
| 双人协作 | BASELINE | 没有房间、实时状态同步、费用请求、标记、重连、暂停协商或双方确认倍速。 |
| 素材 | BASELINE | GitHub 中只有素材说明；`assets/ui`、`assets/chibi` 被忽略且不在当前仓库树里。现有 Spine 加载器会在缺少本机客户端提取物时失败。提取器输出目录与 `002_amiya` 这类运行时目录约定不一致。 |
| 验证 | PASS（仅限当前检查） | 现有 CI 的模块语法检查与足球规则单测通过；它们没有验收部署、技能、AI、多人协作、图像加载或整场玩法。 |

### 根因

1. 当前主循环把“手动操纵小人移动”作为核心；官方阵地足球的核心则是干员编队、部署/撤退、自动攻击、技力/技能，以及足球与单位碰撞/位移的联动。
2. 当前球场规则与技能、部署费用、再部署、屏障、球队行为彼此割裂。继续往 `main.js` 堆条件会持续造成规则冲突；需要将规则改为可测试的纯模块，由渲染/输入层驱动。
3. 本机提取器没有生成可验证的 asset manifest，且 Spine 骨骼的输出路径/文件命名不能直接满足页面的 `/chibi/<operator-id>/` 访问方式。
4. “六种风格图标可点击”不代表风格实现完成；真正机制包括负面效果、携带物触发、范围/时长、技力/治疗等与单位状态的交互。
5. 官方是 2 人合作作战；单浏览器模拟不能被标成在线双人完整实现。协作同步与战斗规则必须分层处理。

## 2. 目标架构

- `data/football/`: 可追溯的足球类型、风格/携带物、球队、关卡阶段配置；官方已知数值集中为数据，不散落在 UI。
- `lib/football/`: 纯函数系统：match state/reducer、部署/费用/再部署、SP/技能、球物理/阻挡/位移、碰撞伤害/喘息、射门/结算、AI 战术。
- `lib/football/assets.mjs`: 本机官方素材优先、仓库原创资源回退；启动时校验资源清单，缺失资源在 HUD 报告，不让干员静默消失。
- `main.js`: 保留现有 Three/Pixi 场景渲染、输入到命令的适配，不再持有所有玩法规则。
- `server/room-server.py`: 可选、最小的 WebSocket 房间/状态中继；只处理房间、玩家所有权、状态包、重连/断线，不把战斗规则复制到服务器和浏览器两份。
- `tools/extract-assets.py` + `tools/check-assets.py`: 从用户本机已安装客户端提取版权素材到 git-ignored `assets/local/` 并验证名称/尺寸/数量；不向公开仓库提交官方角色图、音频、贴图。
- `assets/public/`: 可随仓库分发的原创 SVG/程序化素材，包括球场背景、十种球的图标、六种风格/携带物图标、角色职业占位精灵、按钮/HUD 缺失回退。官方提取资源优先显示。

## 3. 分阶段执行清单

### Phase A — 规则数据与测试基线
- [ ] 从 PRTS 规则和仓库已有 `level_act1multi_football.json` 建立配置清单，标明来源与不确定项。
- [ ] 修正十种足球参数/重量/碰撞/推动阈值/特殊效果；增加重量对应的位移带球判定。
- [ ] 将三种阶段的参数做成显式配置；所有官方数值必须来自来源，不确定的单位换算需标记为校准值。
- [ ] 为球、比分、推动方向、阻挡、阶段结束、全员撤退建立纯函数单测。

### Phase B — 官方作战循环
- [ ] 移除摇杆作为主要战斗控制；保留底座风格的格点、角色朝向、动画状态和路径/动作更新逻辑。
- [ ] 实现待部署池、拖放预览、合法部署格、部署费用增长、部署/撤退、再部署计时与部署上限。
- [ ] 实现 SP、初始技力、自动/手动技能、技能 CD、攻击目标选择；将位移技能的位移距离与球重量联动。
- [ ] 实现球占用 3 阻挡、单位剩余阻挡要求、守门位额外阻挡且不占部署位。
- [ ] 每次进球后，所有在场干员撤退并进入再部署计时；更新比分、重置球/屏障并继续比赛。
- [ ] 费用/技力加成从关卡模式配置读取；特级赛不套用官方注明不适用的技力需求折扣。

### Phase C — 球员 AI 与场地机制
- [ ] 四种正式对手球队数据化：标准队、战术队、爱球会、球德联。
- [ ] 三种敌方分工：击球手、守门员、击人手，目标函数各自不同；球队随机选择可用策略。
- [ ] 实现击人、足球冲击、喘息/恢复、阵地屏障由单位/足球破坏、球门威胁单位与可配置额外敌人。
- [ ] 实现每种足球的完整公开参数/特殊效果，并以数据驱动球体外观和场地地形痕迹。

### Phase D — 六种比赛风格与携带物
- [ ] BASIC：我方攻击力 +10%；赛场啦啦队携带物按官方触发规则实现。
- [ ] ANCHORING：在场攻击力/最大生命逐步增长至 +60%，再部署时间 +15%；护具分发员屏障效果。
- [ ] ROAMING：再部署 -20%、初始技力 +10、部署上限 -1；混乱烟花箱效果。
- [ ] OFFENSIVE：攻速 +20、造成伤害时 10% 概率回复 1 SP、我方受伤 +20%；猛兽能量饮料效果。
- [ ] SUPPORTIVE：治疗 +40%、攻击范围内我方额外每秒 +1 SP（不叠加）、伤害 -10%；喷射汽水机效果。
- [ ] DISABLING：我方控制异常时长 +150%、对未处于控制异常的敌人伤害 -15%；迷幻反射镜效果。
- [ ] 携带物按真实部署事件、目标范围、持续时间/冷却执行；不能只是按钮或一次性日志。
- [ ] 风格效果单测覆盖正面与负面效果、边界状态和多人所有权。

### Phase E — 双人协作
- [ ] 房间创建/加入与玩家席位（两位玩家）。
- [ ] 双端共享唯一的 match-state；部署意向与部署事件同步，不允许客户端分别模拟出不同球位置。
- [ ] 费用请求/同意或拒绝/15 秒冷却、标记、协同暂停申请与恢复、双方确认倍速。
- [ ] 掉线后已部署单位继续行动；在恢复窗口内重连；双方掉线时自动暂停。
- [ ] 对协议事件与状态机写离线模拟测试；提供只在本机启动的服务器，不引入 Docker/数据库/Redis。

### Phase F — 素材与运行包
- [ ] 修正提取器的输出目录与角色 ID、Spine skeleton/atlas/纹理映射，产出 `assets-manifest.json`。
- [ ] 增加检查脚本：按角色清单检验 .skel/.atlas/.png，检验 HUD/场地/声音资源；给出可复制的修复命令。

- [ ] 本地官方素材优先覆盖原创回退；公开 repo 不包含用户从游戏客户端解出的版权二进制。
- [ ] 增加启动诊断：当前使用 official-local / public-fallback 的资源数量与缺项清单。

## 4. 验收标准（不以“界面有按钮”代替通过）

1. 全新克隆没有官方本机素材时，依然能显示球场、干员占位精灵、足球、HUD、风格与携带物图标；不能请求不存在的资源作为唯一渲染路径。
2. 启动可选初级/高级/特级阵地足球；使用正确的关卡参数和 1/2/4 净胜球印章门槛。
3. 干员必须从待部署池部署；费用、技力、技能、撤退、再部署与进球后全员撤退形成闭环。
4. 足球的 10 类公开参数、阻挡/守门/位移技能、进球倍数及地形效果有自动化测试。
5. 对手队伍行为能通过确定性测试证明有差异，而不是仅随机换颜色/标签。
6. 六种风格的正面、负面效果及其携带物均由真实事件触发并通过测试。
7. 两个客户端同一房间对部署、技能、球位置、比分和比赛阶段保持一致；断线恢复不会重复扣费/重复进球。
8. 所有未能取得精确官方数值或无法从本机客户端提取的资源必须标记为 PENDING，不得以近似值宣称官方复刻。

## 5. 本轮执行顺序

1. 先提交本计划（只改文档）作为审计基线。
2. 然后执行 Phase A + Phase F 的本仓库可执行部分，为规则和素材建立可靠底座。
3. 继续执行 Phase B/C/D，将玩法从“手控小人足球”改为“部署/自动作战”。
4. 最后做双人协作协议与端到端验收；每个阶段单独提交并查看 CI。若需要本机客户端素材生成，自动化脚本会在当前开发机做能力内的验证，并清晰标出哪些文件必须由用户现有客户端生成。
