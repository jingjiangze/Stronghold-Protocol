# 拉模式审计：哪些流能改成「用户读取，服务器不主动发」

**本文只审计，未实施。** 对象：现有四层里所有**服务器主动推送**的流。

---

## 1. 成本模型：为什么「改成拉」通常不省

设 N 个接收者、某状态的变化率 R（次/秒）：

| 模式 | 每接收者成本 | 同等新鲜度 |
|---|---|---|
| **推** | R × 帧大小 | 需要多新就多新 |
| **拉** | P × 帧大小（P = 轮询率） | 要追上 R 就得 **P ≥ R** |

⇒ **要同等新鲜度，拉 ≥ 推**（还要加上每次请求的 RTT 与头部开销）。

**拉只在一种情况下赢：接收方不需要新鲜度。** 三种：(a) 没在看的人；(b) 从不进对局的第三方；
(c) 客户端很少打开的面板。下面按这三类逐个审。

---

## 2. 逐个流的裁决

| 流 | 现状 | 改成拉？ | 判断 |
|---|---|---|---|
| **`m.public`** | 推，0.84 帧/s，delta+压缩后约 3 B/s | ❌ | 它是 HUD：LP / 倒计时 / boss 血条。要求「变化即见」，拉没有空间 |
| **`m.private`** | 推，0.64 帧/s，压缩后约 23 B/s | ❌ | 商店/手牌/棋盘。点开面板才拉 = 打开瞬间空一帧，玩家看得见 |
| **`b.start`** | 推，每场次每人一次，4.2 KB，**未压缩** | ❌（但该**加进压缩白名单**） | 客户端要靠它本地推演，必须在开打前到；**它现在的 72.5 B/s 是没被压缩造成的，不是推造成的** |
| **`b.snap`/`b.ev`** | 推，服务端跑战斗的场才有 | ⚠️ 半 | 只有**观战者**可降频（已做：5 Hz）。但战斗画面要连续，不能改成拉 |
| **羁绊表 `bonds`** | 随 `m.public` 推（已按收件人裁剪） | ❌ **明确不做** | 反向做「按需拉羁绊」= 点开队友/单位卡时**短暂空或旧**的羁绊条 —— 可见的退化 |
| **`m.ticker` / `m.toast`** | 推，偶发，极小 | ❌ | 量级太小（<5 B/s），不值得动 |
| **`room.state`** | 推，极小 | ❌ | 同上 |
| **大厅/房间列表** | 客户端 60 s 自报 + 聚合 | ✅ **已经是拉** | 已有实现，无需改 |
| **第三方只读**（状态页、大厅站、mod 管理器） | 过去只能开一个 WS 会话去读 | ✅ **应是拉** | 见 §3 |

## 3. 两个真正的机会（都不牺牲新鲜度）

### 3.1 隐藏标签页：停推，回前台重同步（最大的一项）

**依据**：客户端**已有** `visibilitychange` 钩子（`public/js/net.js`），目前只用来抑制链路探测。

**做法**：标签页隐藏 → 客户端发一个轻量 intent → 服务端对该连接**停推或大幅降频**；
回前台走**已有的 resync**（`_resync()` 第一件事就是发完整 `m.public`）拿全量。

**为什么它安全**：玩家看不见的时候，帧迟到没有观感成本；回来的那一帧本来就是全量基线。

**收益量级**：省的是「人不在」的时段。对常挂后台的玩家（开着别的窗口）可以是整段时间的 100%，
对一直盯着的玩家是 0。**无需猜——上线后由 stats 告诉我们分布**（这正是只读接口的
`framesSkipped` / `framesSent` 计数器存在的意义）。

### 3.2 第三方读取：走只读路由，不占会话

**依据**：本仓历史上核过这件事 —— 观察者**从来不持有游戏会话**，而外部工具要读状态只能
自己开一个 WS，然后收下它根本不需要的全部帧。

**做法**：就是本包的 `/ws-compression/*` 那条模式 —— 精确路径、只读 JSON、无会话。

**为什么值得**：它不是「省带宽」，而是**把一类接收者从上行里彻底移除**。一个挂在旁边的状态页
原本要 105 B/s 的会话，现在是一次 HTTP 请求。

## 4. 与冷启动那笔账的关系（顺带纠正一个直觉）

把 60 分钟口径摆在一起看：

| 项 | 每人 | 备注 |
|---|---|---|
| 对局稳态（已压缩） | **105 B/s** | 实测 |
| 新玩家冷启动摊到 60 分钟 | **1,573 B/s** | 客户端 5.4 MB，浏览器缓存后才归零 |

⇒ **冷启动比对局流量贵 15 倍。** 所以「省带宽」的优先级应当是：

1. **把客户端静态也交给 CDN**（现在是 Cloudflare `MISS` + 盒子自己发）—— 收益是**一个数量级**
2. **`b.start` 加进压缩白名单**（实测可省 60.2%，一行代码）—— 从 72.5 → 约 29 B/s
3. 隐藏标签页停推（量级取决于分布，待测）
4. 再往下才是「把某个流改成拉」—— 而按 §1 的模型，它多半不省

---

## 5. 结论

- **「改成拉」不是一条通用省流路线**：同等新鲜度下拉 ≥ 推，只有在接收方不需要新鲜度时才赢。
- **真正该做的两件是「隐藏标签页停推」和「第三方走只读路由」**；两者都不牺牲任何人的观感。
- **最大的一笔根本不在推/拉，而在静态资源的分发位置**（§4）。
- 明确**不做**：按需拉羁绊（可见退化）、把 `m.public`/`m.private` 改成拉（HUD 与面板都要即时）。
